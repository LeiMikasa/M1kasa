## 2. 目标链路是什么

```text
用户提交 liked=true 或 liked=false
    ↓
Redis Lua 更新状态、总数、版本、Outbox
    ↓
HTTP 返回当前 Redis 结果

后台扫描 Outbox
    ↓
Publisher 发送点赞变更消息
    ↓
RabbitMQ 发布确认成功，且没有消息退回
    ↓
Lua 比较并清理已发送的那一份 Outbox 记录

RabbitMQ 投递给消费者
    ↓
数据库事务：版本判断 + 点赞关系更新 + 总数变更
    ↓
事务提交，监听方法正常返回
    ↓
Spring 发送消费 ACK
```

消费者更新的是 MySQL。Redis 已经在用户操作时更新，不能在消费同一个变更时再给 Redis 加减一遍。

Redis Outbox 删除代表发布检查通过，不代表 MySQL 已经更新。数据库提交与消费 ACK 之间仍可能发生故障，消息重投递时要依靠消费幂等。

## 3. 三个容易混淆的“确认”

| 名称 | 谁确认什么 | 不代表什么 |
| --- | --- | --- |
| 发布确认 Publisher Confirm | RabbitMQ 向生产者确认发布结果 | 不代表消费者已提交数据库事务 |
| Outbox 确认清理脚本 | 应用检查 Redis 中是否仍是本次已确认发送的那份记录 | 不是向 RabbitMQ 发送 ACK |
| 消费确认 Consumer ACK | 消费者容器通知 RabbitMQ 当前投递已处理完成 | 不是生产者的发布确认 |

`BlogLikePublisher` 中检查的 `confirm.ack()` 属于第一种。`blog_like_outbox_ack.lua` 属于第二种。`acknowledge-mode: auto` 管理的是第三种。

发布确认和消费确认是两个独立阶段。[RabbitMQ 确认机制说明](https://www.rabbitmq.com/docs/confirms#are-publisher-confirms-related-to-consumer-delivery-acknowledgements)

### 两种消息 ID

```text
业务消息 ID：blog-like:10:1001:3
发布确认 ID：每次发送生成一个新的 UUID
```

同一个用户对同一篇笔记的同一版本重发，业务消息 ID 保持不变；每次发布尝试的确认 ID 重新生成。业务消息 ID 用于标识和追踪事件，不能代替数据库版本判断。

## 4. “MQ 自己的重试发生在哪里？”

要分清四种机制：

| 机制 | 发生位置 | 触发条件与作用 |
| --- | --- | --- |
| `template.retry` 发送重试 | 生产者 JVM 内的 Spring AMQP | 应对发送调用抛出的可重试异常，例如部分连接故障 |
| Redis Outbox 重发 | 我们编写的定时任务 | 记录仍在就有机会继续发送；任务必须实际进入投递流程 |
| `listener.simple.retry` 消费重试 | 消费者 JVM 内的 Spring AMQP | 对抛出可重试异常的消费处理进行本地重试 |
| RabbitMQ 重新投递 | Broker | 例如消费者连接关闭时，未确认投递重新入队 |

### 4.1 发送端有重试吗

Spring 支持发送重试，配置位置是：

```yaml
spring:
  rabbitmq:
    template:
      retry:
        enabled: true
        max-retries: 2
        initial-interval: 1s
        multiplier: 2
        max-interval: 5s
```

这是讨论过的可选配置，整理时本地内容服务没有显式开启。它针对发送操作异常；不能把异步 NACK、消息退回、发布确认 Future 超时，都理解成会自动重新调用业务 `send()`。

Outbox 用于保留可重发的业务记录；短暂的内存重试不能替代它。[Spring Boot AMQP 说明](https://docs.spring.io/spring-boot/reference/messaging/amqp.html)

### 4.2 `orTimeout()` 会自动重发吗

不会。当前发布代码的核心是：

```java
return correlationData.getFuture()
        .orTimeout(5, TimeUnit.SECONDS)
        .thenApply(confirm -> {
            if (correlationData.getReturned() != null) {
                throw new IllegalStateException("消息无法路由到队列");
            }
            if (!confirm.ack()) {
                throw new IllegalStateException("发布未获确认");
            }
            return null;
        });
```

- `orTimeout()`：Future 未及时完成，就以超时异常完成。
- `thenApply()`：确认到达后检查结果，不执行重新发送。
- 这个 5 秒约束的是确认 Future，不是整个业务的端到端耗时上限。
- 超时不等于 RabbitMQ 一定没收到消息，后续重发可能产生重复消息。

重发与重复消息需要配套幂等处理。[RabbitMQ 生产者可靠性说明](https://www.rabbitmq.com/docs/reliability#data-safety-on-the-publisher-side)

### 4.3 消费失败会让生产者重发吗

普通消费重试不会要求生产者重发。消息已经到达消费者，Spring 在消费者端再次调用处理逻辑。重试期间这次投递尚未成功确认。

消费者崩溃或断连导致未确认消息重新入队，是另一种 Broker 重新投递机制。[未确认消息的自动重新入队](https://www.rabbitmq.com/docs/confirms#automatic-requeueing)

## 5. Dispatcher 为什么发送成功后还不能直接 HDEL

它接收一条原始记录：

```java
dispatcher.dispatchOne(
        10L,          // 笔记 ID
        1001L,        // 用户 ID
        "1:3:1000"    // 已读取的原始状态：点赞、版本3、时间1000
);
```

执行顺序：

```text
解析 originalState → 组装消息 → publisher.send()
    ↓ Future 正常成功
thenRun() → 比较并清理原记录
```

发送期间，用户可能取消点赞：

```text
本次发送：1:3:1000
    ↓
用户取消：Outbox 被更新成 0:4:2000
    ↓
旧版本3获得发布确认
```

如果直接 `HDEL outboxKey userId`，就会删除尚未发送的新版本4。

正确做法是比较完整原始字符串，相同才删除。完整脚本如下：

```lua
-- KEYS[1]：点赞 Outbox Hash
-- ARGV[1]：用户 ID，也就是 Hash 字段
-- ARGV[2]：本次已经发送并获得确认的原始记录

local outboxKey = KEYS[1]
local userId = ARGV[1]
local expectedState = ARGV[2]

-- 读取现在的待发送记录
local currentState = redis.call('HGET', outboxKey, userId)

-- 只有记录仍然相同，才删除
if currentState == expectedState then
    return redis.call('HDEL', outboxKey, userId)
end

-- 已被其他任务删除，或者已经产生了更新版本
return 0
```

| 返回值 | 解释 |
| --- | --- |
| `1` | 当前值仍然等于本次发送值，原记录已删除 |
| `0` | 当前记录已变化或已不存在，不进行删除；属于正常结果 |

这里比较的是整段 `状态:版本:时间`，不是只比较版本号。Lua 保证比较和删除之间不插入其他 Redis 命令，但不提供数据库事务那样的出错回滚。[Redis Lua 执行说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

### `thenRun()` 与 `join()`

```java
publisher.send(message).thenRun(() -> {
    // 发布 Future 正常完成后，才执行清理
});
```

前一步失败，清理回调跳过；回调自身抛异常，返回的 Future 也会失败。

```java
dispatcher.dispatchOne(blogId, userId, originalState).join();
```

后台任务等待的是这条记录的“发布检查和后续清理”，不是消费者完成 MySQL 更新。当前任务逐条等待，并没有因为使用 Future 就自动并行发送所有记录。

## 6. ScanOptions 和 Cursor 到底做了什么

### 6.1 这段代码只是在生成规则

```java
ScanOptions options = ScanOptions.scanOptions()
        .match(OUTBOX_PREFIX + "*}")
        .count(100)
        .build();
```

前缀为 `m1kasa:blog:like:outbox:{`，所以最终模式是：

```text
m1kasa:blog:like:outbox:{*}
```

会匹配 `outbox:{10}`、`outbox:{20}` 等完整 Key 名称。`*` 不限定内容必须为数字，因此 Java 后续还要解析和校验笔记 ID。

`.build()` 只构造配置，真正的扫描由 `stringRedisTemplate.scan(options)` 发起。

### 6.2 是不是调用 scan 时就先查100个

按项目当前 Spring Data Redis 4.1.1 + Lettuce 的实现，创建并打开 Cursor 时会先发起第一批 SCAN，类似：

```redis
SCAN 0 MATCH m1kasa:blog:like:outbox:{*} COUNT 100
```

但 **COUNT 100 是工作量提示，不保证返回100个匹配 Key，也不是整个任务只处理100条。** 一批可以返回很少的匹配项，甚至0个；游标未结束时仍需继续扫描。[Redis SCAN 与 COUNT 说明](https://redis.io/docs/latest/commands/scan/)

```java
try (Cursor<String> keys = stringRedisTemplate.scan(options)) {
    while (keys.hasNext()) {
        String outboxKey = keys.next();
        // 处理当前 Key
    }
}
```

```text
scan(options)：获取第一批结果和后续游标
    ↓
next()：从当前批次取一个 Key
    ↓
当前批次取完
    ↓
hasNext() 根据游标自动继续获取下一批
    ↓
扫描结束且结果耗尽，hasNext() 返回 false
```

不是每执行一次 `next()` 就访问一次 Redis。`try-with-resources` 用于结束时关闭游标并释放相关资源。

### 6.3 为什么有两层扫描

```text
外层 SCAN：寻找各篇笔记的 Outbox Key
    m1kasa:blog:like:outbox:{10}
    m1kasa:blog:like:outbox:{20}

内层 HSCAN：读取某一个 Outbox Hash 的字段和值
    1001 → "1:3:1000"
    1002 → "0:2:2000"
```

HSCAN 的返回内容用于组成 `blogId + userId + originalState`，再交给 Dispatcher。[Redis HSCAN 说明](https://redis.io/docs/latest/commands/hscan/)

### 6.4 扫描有什么优势和成本

- 分批遍历，比单次 KEYS 查询全部匹配键更容易控制单次命令占用时间。
- Java 可以边读取边处理，无需先保存全部匹配 Key。
- 不需要每轮查询 MySQL 的全部笔记来枚举 Outbox。
- MATCH 是返回结果过滤，不是前缀索引；当前外层完整 SCAN 仍遍历 Redis 数据库的键空间。
- SCAN 不是业务快照，可能返回重复结果；变更中的数据可能在后续轮次才被处理。

因此不能把“扫到一次”理解成“全链路恰好处理一次”。本段扫描按当前单节点 Redis 使用方式理解，不能直接据此声称已覆盖 Cluster 的所有节点。[Redis SCAN 保证](https://redis.io/docs/latest/commands/scan/#scan-guarantees)

### 6.5 定时任务真的是严格每两秒跑一次吗

```java
@Scheduled(fixedDelay = 2000, initialDelay = 5000)
```

含义是启动后首次等待5秒，每轮执行结束后再等2秒。如果一轮逐条等待发布确认耗时10秒，下一轮不会在本轮中途按两秒间隔重新启动。

## 7. 版本判断与计数增量怎么配合

消费者先读取数据库关系，再比较：

```java
if (message.version() <= oldVersion) {
    return;
}
```

旧版本和重复版本正常忽略；新版本保存目标状态、版本和事件时间。

总数按状态差计算，不按消息次数或版本差计算：

```java
int delta = (newLiked ? 1 : 0)
        - (oldLiked ? 1 : 0);
```

| 原状态 | 新状态 | delta |
| --- | --- | --- |
| 未点赞 | 已点赞 | `+1` |
| 已点赞 | 未点赞 | `-1` |
| 未点赞 | 未点赞 | `0` |
| 已点赞 | 已点赞 | `0` |

Outbox 可以合并同一用户的连续状态，消费端不要求版本逐个连续到达。

例如数据库尚无关系，直接收到“未点赞、版本2”：应新增未点赞关系、保存版本2，总数不变。否则之后迟到的“点赞、版本1”可能被错误接受。

即使 delta 为0，只要是更新版本，也要保存版本。每对 `(blog_id, user_id)` 应有联合唯一索引。

## 8. “一个事务不就够了，为什么还要 FOR UPDATE？”

两者解决的问题不同：

| 机制 | 本例中的作用 |
| --- | --- |
| 数据库事务 | 点赞关系和总数一起提交或回滚 |
| 锁定读取 | 协调并发事务，保护读取、Java 判断、更新这一段过程 |

`@Transactional` 不会自动把多个消费者的整段 Java 方法串行执行。普通读取与写入之间，别的事务仍可能完成更新。

例子：数据库最初为“未点赞、版本2”，总数20。

| 顺序 | 消费者 A：点赞版本3 | 消费者 B：取消版本4 |
| --- | --- | --- |
| 1 | 普通 SELECT 读到未点赞、版本2 | 普通 SELECT 也读到未点赞、版本2 |
| 2 | 判断新版本，计算 delta=+1 | 判断新版本，计算 delta=0 |
| 3 | 保存已点赞版本3，总数变21并提交 | |
| 4 | | 根据旧判断保存未点赞版本4，总数仍21 |

最终状态是未点赞，却残留了多加的一次计数。即使 UPDATE 阶段等到了数据库锁，也不会自动重新执行此前的 Java 判断。

这个例子说明的是默认隔离级别下，多步读取与更新需要并发控制；不是说所有事务设计都只能用 FOR UPDATE。不同隔离级别和条件更新也可以形成其他正确方案。[InnoDB 普通一致性读取](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)

## 9. “一条消息怎么可能被两个消费者处理？”

正常竞争消费时，同一队列中的一次投递交给一个消费者，不是广播给所有消费者。[RabbitMQ 工作队列说明](https://www.rabbitmq.com/tutorials/tutorial-two-java)

并发可能来自：

1. 同一业务事件被重复发布成两份消息，例如发布确认丢失、Outbox 清理失败后重发，或多个任务同时投递同一条记录。
2. 两条正常的不同版本消息，例如点赞版本3、取消版本4，在多个消费者上并行执行。

```text
同一业务事件的副本1 → 消费者A
同一业务事件的副本2 → 消费者B
```

不能把它说成“一份普通消息正常情况下同时广播给两个消费者”。确认丢失后的重发可能产生重复，这也是消费端需要幂等的原因。[RabbitMQ 可靠性说明](https://www.rabbitmq.com/docs/reliability)

### 当前单线程是不是没这个并发问题

如果只有一个服务实例、一个同步消费线程，而且相关写入都经由这个串行入口，消息会逐条执行；上述两个消费者同时读取的场景不成立。

因此，显式行锁是当前实现为并发消费选择的一种保护，不是因为“用了 MQ 就必然要加”。以后增加消费线程、多个服务实例或其他写入入口时，需要重新核对并发假设。

## 10. “FOR UPDATE 锁住当前一行吗？另一个还能读吗？”

本例 SQL：

```sql
SELECT id, liked, version
FROM tb_blog_like
WHERE blog_id = 10
  AND user_id = 1001
FOR UPDATE;
```

使用完整联合唯一索引且关系已存在时，可以理解为锁定对应关系记录；InnoDB 实际锁定相关索引记录。主键查询已有笔记也是类似情况。

| 另一个事务的操作 | RR/RC 下的通常行为 |
| --- | --- |
| 普通 SELECT | 可以通过 MVCC 读取可见快照 |
| 对同一记录 SELECT ... FOR UPDATE | 在锁定读取阶段等待 |
| 修改或删除同一记录 | 等待冲突锁释放 |

锁持续到事务提交或回滚。范围查询、记录不存在或索引不合适时，锁范围可能涉及间隙或更多索引记录，不能把所有 FOR UPDATE 都解释成只锁一个已有行。[InnoDB 锁定范围](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)

### “如果 B 先读完比较，再等着修改呢？”

这正是普通快照 SELECT 可能产生的问题。两个消费者都执行当前代码的锁定读取时，B 会在查询处等待，还没有拿到结果，因此后面的 Java 比较尚未执行。

```text
A：FOR UPDATE 读到未点赞版本2，持锁
B：FOR UPDATE 等待，查询尚未返回
A：保存已点赞版本3，总数+1，提交并释放锁
B：获得锁，读取已点赞版本3
B：处理取消版本4，计算 delta=-1，提交
```

FOR UPDATE 是锁定读，也称当前读。在这个例子中，B 等待后读取 A 已提交的新状态，不沿用先前的旧判断。当前 Service 还会先锁笔记行，所以 B 可能更早就在笔记查询处等待。[MySQL 锁定读取说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)

## 11. “用普通 Java 锁，集群用分布式锁不行吗？”

可以，但要明确锁的作用范围和事务边界。

| 方案 | 作用范围 | 释放方式 |
| --- | --- | --- |
| synchronized / ReentrantLock | 同一个 JVM 内共享同一锁对象的线程 | 应用代码控制 |
| Redisson 分布式锁 | 多个应用实例通过 Redis 协调 | 应用控制，并处理锁生命周期 |
| MySQL 行锁 | 访问同一 MySQL 数据的多个事务，包括不同应用实例 | 事务提交或回滚时释放 |

数据都在同一 MySQL 时，行锁本身就能跨应用实例协调，不需要因为服务部署成集群就必然换成 Redis 锁。

另一个难点是解锁时机。如果在 `@Transactional` 方法体内获取应用锁，再在 finally 中释放，可能发生：

```text
业务方法 finally 释放 Java/Redis 锁
    ↓
业务方法返回给 Spring 事务代理
    ↓
Spring 才提交数据库事务
```

应用锁要正确覆盖事务完成边界；单纯把 FOR UPDATE 替换成方法内部的锁，不一定保留原有保护效果。当前实际实现仍使用数据库锁，没有改成 Redisson。

## 12. “数据库行锁会死锁，是不是不太好？”

锁等待和死锁不同：

```text
正常等待：A持锁，B等A；A可以继续完成并提交。

死锁示例：
A持有笔记锁，等待关系锁；
B持有关系锁，等待笔记锁。
双方形成循环等待。
```

当前统一顺序是先锁笔记、再锁关系。这个顺序用于减少相反加锁造成的冲突，但不是无死锁保证。

可采取的措施：

- 所有相关写入入口尽量统一访问与加锁顺序。
- 事务保持短小，里面不等待 MQ 发布、RPC 或其他耗时外部操作。
- 配置合适索引，减少扫描和锁定范围。
- 死锁异常向外抛出，回滚后重试整笔事务，不只重试最后一条 SQL。

InnoDB 默认启用死锁检测，会回滚事务来解除循环等待。[死锁检测说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlock-detection.html) 短事务、统一顺序、索引和事务重试也是官方建议。[减少与处理死锁](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks-handling.html)

当前实现偏保守：先锁笔记，会让同一篇热门笔记的数据库消费串行。它有正确性方面的直观优势，也可能形成热点等待，不能据此声称吞吐已经优化到最好。

后续可评估版本 CAS、缩小提前加锁范围或批量处理。但条件更新也要正确处理影响行数、状态增量与重试；UPDATE 本身仍有数据库锁，不能说改成乐观方式就没有任何死锁。

## 13. 消费者配置逐项解释

以下片段放在 `spring.rabbitmq` 下：

```yaml
listener:
  type: simple
  simple:
    acknowledge-mode: auto
    default-requeue-rejected: false
    prefetch: 10
    retry:
      enabled: true
      max-retries: 2
      initial-interval: 1s
      multiplier: 2
      max-interval: 5s
```

| 字段 | 含义 |
| --- | --- |
| `type: simple` | 使用 SimpleMessageListenerContainer |
| `acknowledge-mode: auto` | Spring 根据监听方法是否正常返回管理确认 |
| `default-requeue-rejected: false` | 最终拒绝时不放回原队列；不关闭本地重试 |
| `prefetch: 10` | 每个消费者最多保持10条已投递、尚未确认的消息 |
| `retry.enabled: true` | 开启消费端本地重试 |
| `max-retries: 2` | 首次失败后最多再试两次 |
| `initial-interval: 1s` | 首次重试前等待1秒 |
| `multiplier: 2` | 后续等待间隔乘2 |
| `max-interval: 5s` | 单次等待间隔上限5秒 |

### 重试两次到底一共处理几次

以可重试业务异常为例：

```text
首次执行失败，事务回滚
    ↓ 等1秒
第1次重试失败，事务回滚
    ↓ 等2秒
第2次重试仍失败，事务回滚
    ↓
重试耗尽，拒绝消息
    ↓
按已配置且正常工作的死信路由进入DLQ
```

最多处理3次；任意一次成功，就结束重试并进入确认流程。当前两次等待是1秒、2秒，尚未触及5秒上限。Spring Framework 的 maxRetries 不包含首次调用。[重试次数定义](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/core/retry/RetryPolicy.Builder.html#maxRetries(long))

这里使用项目的 Boot 4 配置名称，不要与旧版本配置中的 max-attempts 混用。

### prefetch: 10 为什么不等于10并发

假设只有一个处理线程，队列最初有100条消息：

```text
RabbitMQ先陆续投递10条
    ↓
消费者手里：1条在handle()，其余9条等待处理
    ↓
这10条都未确认时，暂不继续给该消费者第11条
    ↓
第1条处理完成并ACK，未确认数变9
    ↓
MQ可以补发1条，未确认数再次达到10
```

这是未确认投递额度，不是必须凑齐的批次，也不是线程数。收到一条就能处理；不用等10条全部完成才继续补发。并发数量由 concurrency 等配置控制。[RabbitMQ Consumer Prefetch](https://www.rabbitmq.com/docs/consumer-prefetch)

## 14. AUTO 是不是成功消费之后才 ACK

在当前“同步监听器调用独立事务 Service”的代码结构下：

```text
handle() 收到消息
    ↓
syncService.sync() 执行数据库事务
    ↓
事务提交成功，Service调用正常返回
    ↓
handle() 正常返回
    ↓
Spring 容器发送消费 ACK
```

Spring 判断的依据是监听调用正常返回或抛异常。AUTO 是容器管理确认；RabbitMQ 协议里的 autoAck=true 对应 Spring 的 NONE，不能混成同一种模式。[Spring AcknowledgeMode 定义](https://docs.spring.io/spring-amqp/docs/current/api/org/springframework/amqp/core/AcknowledgeMode.html)

当前监听代码保留异常传播：

```java
public void handle(BlogLikeChangedMessage message) {
    syncService.sync(message);
    // 正常返回后，容器才按AUTO模式确认
}
```

旧版本或重复版本被 Service 正常忽略，也属于处理完成，会被 ACK。

下面的写法则可能造成误确认：

```java
try {
    syncService.sync(message);
} catch (RuntimeException ex) {
    log.error("失败", ex);
    // 只记录日志，没再抛出异常
}
// 方法正常返回，容器可能将其当作成功
```

MySQL 提交后、消费 ACK 到达 Broker 前断连，仍可能重新投递。当前方案没有把 MySQL 提交与 RabbitMQ ACK 放进一个全局事务，版本幂等需要保留。

## 15. 消费失败最终进入哪里

当前点赞拓扑名称：

| 用途 | 名称 |
| --- | --- |
| 业务交换机 | `m1kasa.blog.like.exchange` |
| 业务路由键 | `blog.like.changed` |
| 业务队列 | `m1kasa.blog.like.changed.queue` |
| 死信交换机 | `m1kasa.blog.like.dlx` |
| 死信路由键 | `blog.like.failed` |
| 死信队列 | `m1kasa.blog.like.dlq` |

业务队列通过 @RabbitListener 的 @QueueBinding 声明；死信交换机、队列和绑定通过配置类的 Declarables 声明。声明死信队列不等于为它创建消费者。

在当前默认失败恢复策略下，可重试异常耗尽后拒绝且不重新入队；配置正常的 DLX 路由才能转入死信队列。没有死信路由时，被拒绝的消息可能被丢弃。[Spring Boot 消费失败处理](https://docs.spring.io/spring-boot/reference/messaging/amqp.html#messaging.amqp.receiving)

生产者发布失败不直接进入这里的消费死信队列；仍由 Outbox 保留记录重试。当前订单死信采集任务面向订单队列，不会自动采集点赞 DLQ。

## 17. 回看时最容易记错的结论

| 疑问 | 结论 |
| --- | --- |
| Future 超时是不是自动重发 | 不是；由失败处理和Outbox任务安排再次发送 |
| 发布ACK是不是数据库已更新 | 不是，它是生产者与Broker之间的确认 |
| Outbox ACK脚本是不是消费ACK | 不是，它是Redis记录的比较清理 |
| 为什么发送确认后还要比较原记录 | 防止旧确认删除期间产生的新版本 |
| COUNT 100是不是固定返回100个 | 不是，是扫描工作量提示 |
| next()是不是每次都查询Redis | 不是，先取当前批次，耗尽后继续扫描 |
| MATCH是不是只遍历这个前缀 | 不是，它过滤返回结果，完整SCAN仍遍历键空间 |
| 一份消息正常会广播给两个消费者吗 | 同一队列的竞争消费不会；重复副本或不同消息可以并行 |
| 一个事务是不是整段Java逻辑自动串行 | 不是，读取、判断、写入仍要考虑并发 |
| FOR UPDATE是不是禁止其他人普通查询 | RR/RC普通快照查询通常仍可读取 |
| 版本相同的消息是否再加减总数 | 不处理，正常忽略并确认 |
| 新版本状态没变是否还要保存版本 | 要保存，delta可以为0 |
| 单实例单消费线程是否必需显式行锁 | 不因上述消费者并发而必需，需明确其他写入入口 |
| 集群是不是必须换Redisson | 不是，同一MySQL的行锁也可协调多实例 |
| 行锁是不是一定会造成死锁 | 不是；但要减少风险并处理事务重试 |
| prefetch=10是不是开10个线程 | 不是，是未确认投递额度 |
| max-retries=2总共执行几次 | 对可重试失败，最多首次1次加重试2次 |
| AUTO是不是收到消息立刻确认 | Spring按监听结果确认；当前在数据库提交之后 |
| 正常忽略旧消息会不会ACK | 会，这是幂等处理的正常完成 |
| 只打印异常会不会被当作成功 | 有可能，监听器要保留异常传播 |

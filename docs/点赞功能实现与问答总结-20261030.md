## 2. 最后采用的方案与选择原因

目标链路：

```text
用户提交明确的目标状态：点赞 true / 取消 false
    ↓
Redis Lua 检查旧状态
    ↓
状态真的变化时：更新用户状态 + 更新总数 + 递增版本 + 保存待发送记录
    ↓
返回 Redis 当前结果给前端
    ↓
【后续待实现】后台投递 RabbitMQ
    ↓
【后续待实现】消费者按版本处理，持久化关系和计数
```

正常命中 Redis 时，点赞服务不需要同步写 MySQL；第一次加载某个用户对某篇笔记的状态时，可能查询数据库。

今天先讨论过“同步保存点赞关系和计数”，也讨论过“关系同步落库、计数异步”。最后希望通过 Redis 承接请求，再异步写入数据库。

### 数据库压力到底减少在哪里

| 方式 | 数据库主要工作 | 主要取舍 |
| --- | --- | --- |
| 关系和计数都同步写 | 每次有效点赞保存关系，并修改相同笔记的计数行 | 逻辑直观，热门计数行会竞争 |
| 数据库关系 + 数据库 Outbox，计数异步 | 关系和 Outbox 仍同步写，计数可以合并更新 | 改善计数热点，数据库总操作数不一定减少 |
| Redis 承接 + MQ 异步批量落库 | 请求先写 Redis，数据库按消费速度分批处理 | 缓解瞬时写入压力，需要可靠事件和恢复流程 |

例如 1000 个不同用户点赞：最终要持久化时，仍然需要保存这 1000 份有效关系。MQ 可以控制写入节奏，计数可以合并，不能自动消除全部数据库工作量。

同一用户短时间内反复点赞、取消，如果业务只保存最终状态，可以合并尚未发送的变化。这与保存完整操作流水是两种不同需求；当前关系表和 Outbox 主要维护最新状态。

## 3. 数据库记录什么

### 3.1 两类数据

- `tb_blog.liked`：笔记的持久化点赞总数。
- `tb_blog_like`：某个用户对某篇笔记的当前点赞状态、版本和时间。

只有总数，无法判断某个用户是否已经点赞。因此需要关系表。

### 3.2 关系表的目标结构

以下用于说明最终字段；已有表应按实际结构迁移，不需要重复执行建表。

```sql
CREATE TABLE tb_blog_like (
    id BIGINT NOT NULL AUTO_INCREMENT COMMENT '关系记录ID',
    blog_id BIGINT NOT NULL COMMENT '笔记ID',
    user_id BIGINT NOT NULL COMMENT '用户ID',
    liked TINYINT NOT NULL DEFAULT 1 COMMENT '0未点赞，1已点赞',
    version BIGINT NOT NULL DEFAULT 0 COMMENT '该关系的状态版本',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_blog_user (blog_id, user_id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

`liked` 默认 1 是为了兼容最初“表内记录都代表已点赞”的设计。未来消费者写入时，要明确设置实际状态，不能依赖默认值表达取消点赞。

`(blog_id, user_id)` 是联合唯一索引，保证同一对用户与笔记只有一行当前关系。

取消点赞后保留该行，例如：

| blog_id | user_id | liked | version |
| --- | --- | --- | --- |
| 10 | 100 | 0 | 4 |

这行表示“用户100对笔记10最新已处理到版本4，目前未点赞”。它保留版本，方便拒绝旧消息。

后续统计有效点赞关系时需要过滤 `liked = 1`，不能把所有关系行直接计入点赞总数。

## 4. Redis 用了哪几种结构

使用三个 Key、两种数据结构：两个 Hash、一个 String。

假设笔记10有21个赞，用户100已点赞，版本3：

| Key | 类型 | 用途 |
| --- | --- | --- |
| `m1kasa:blog:like:state:{10}` | Hash | 保存各用户对笔记10的状态和版本 |
| `m1kasa:blog:like:count:{10}` | String | 保存笔记10的当前总赞数 |
| `m1kasa:blog:like:outbox:{10}` | Hash | 保存各用户尚待发送的最新变化 |

### 4.1 状态 Hash

```text
Key：m1kasa:blog:like:state:{10}

字段（用户ID）    值
100              1:3:1793361600000
200              0:2:1793361700000
```

值的格式：

```text
点赞状态:版本号:操作时间戳
```

- 1 表示已点赞，0 表示未点赞。
- 版本针对“用户ID + 笔记ID”这对关系。
- 时间戳单位是毫秒。
- `0:0:0` 也是一条有效的已加载状态，表示当前没有点赞历史基准。

状态 Hash 按用户需要加载，并保留未点赞记录，所以 Hash 字段数不等于点赞人数。

### 4.2 计数 String

```text
Key：m1kasa:blog:like:count:{10}
值：21
```

这个值是整篇笔记共享的总数。

### 4.3 Outbox Hash

```text
Key：m1kasa:blog:like:outbox:{10}

字段（用户ID）    值
100              1:3:1793361600000
```

它表示这份最新状态还需要投递。若尚未发送时，用户又取消点赞，字段100可以更新为：

```text
0:4:新的操作时间戳
```

状态 Hash 用来查询当前状态；Outbox Hash 用来驱动同步。后续发布确认通过后，只清理 Outbox 中匹配版本的记录，个人状态和计数继续保留。

三个 Key 的 `{10}` 相同，使它们在 Redis Cluster 中落到同一个槽位，供同一个 Lua 脚本操作。这不会把整个集群变成串行处理。

## 5. setLiked 的实际执行顺序

当前接口采用“设置目标状态”，不采用“每次请求都把状态反转”。

```java
setLiked(10L, true);  // 希望变成已点赞
setLiked(10L, false); // 希望变成未点赞
```

相同请求重复到达时，状态已经相同就保持原样，不重复计数。

当前 Java 流程：

```text
校验笔记ID，读取 UserContext 中的登录用户ID
    ↓
先执行 blog_like_set.lua
    ├─ 数据已准备好：处理请求并返回
    └─ 返回 -2：数据未就绪
          ↓
       initializer.initialize(blogId, userId)
          ↓
       重新执行一次点赞 Lua
          ↓
       返回结果或抛出异常
```

这里只针对明确的 `-2` 初始化后重试一次，没有无限循环，也不会遇到网络错误就自动重放写入。

“先访问 Redis”在两个接口中的意思不同：

- 查询状态：Java 普通 HGET / GET，缺数据时按当前实现调用初始化。
- 提交点赞：Java 先执行点赞 Lua，由 Lua 检查 Redis。不会在 Java 中先单独判断未点赞，再分开增加总数。

## 6. init 到底干什么

最容易记住的解释：

> Redis 尚未准备好数据时，把数据库已有的初始状态补进去；已有数据保留。

初始化加载的是：

1. 数据库的笔记点赞总数。
2. 当前用户对当前笔记的状态。
3. 该关系已有的版本和时间。

Java 查询 MySQL，再把数据作为参数交给 Lua。Lua 本身不会查询 MySQL。

初始化不代表一次有效点赞，不会把总数加一，不递增版本，也不生成新的 Outbox 记录。

### 6.1 初始化 Lua 的参数

| 参数 | 含义 |
| --- | --- |
| `KEYS[1]` | 状态 Hash 的 Key |
| `KEYS[2]` | 总数 String 的 Key |
| `KEYS[3]` | Outbox Hash 的 Key |
| `ARGV[1]` | 用户ID |
| `ARGV[2]` | 数据库点赞总数 |
| `ARGV[3]` | 数据库个人状态，0或1 |
| `ARGV[4]` | 数据库个人状态版本 |
| `ARGV[5]` | 数据库更新时间转换成的毫秒时间戳 |

没有关系记录时，Java 使用“未点赞、版本0、时间0”。有取消点赞的记录时，也要查询出来，沿用其版本。

### 6.2 初始化 Lua 各阶段

| 阶段 | 做什么 |
| --- | --- |
| 接收参数 | 获取三个 Key 和五个初始值 |
| 校验参数 | 用户ID大于0，计数、版本、时间为非负整数字符串，状态只能为0或1 |
| 校验类型 | 状态和Outbox允许不存在或为Hash，计数允许不存在或为String |
| 检查 Key 完整性 | 状态和计数仅剩一个时停止；计数不存在但Outbox仍存在时停止 |
| 检查当前用户 | 计数和个人字段都存在时，直接返回0 |
| 补计数 | 计数不存在时才装入数据库基准值 |
| 补个人字段 | 使用HSETNX补入当前用户，保留已有字段 |
| 返回结果 | 返回1表示本次完成初始化 |

关键代码：

```lua
if not countExists then
    redis.call('SET', countKey, initialCount)
end

redis.call('HSETNX', stateKey, userId, initialState)
```

判断依据是“是否存在”，不是“别人有没有修改过”。例如计数已经存在且值为0，也要保留。

### 6.3 怎么判断没有初始化

点赞脚本当前通过存在性检查判断数据是否就绪，没有额外的 initialized 标记：

```lua
if stateType == 'none' or countType == 'none' then
    return {-2}
end
```

两个 Key 存在后，再检查当前用户：

```lua
local currentState = redis.call('HGET', stateKey, userId)
```

| 结果 | 意思 |
| --- | --- |
| 没有当前用户字段 | 当前用户的数据尚未准备好 |
| `0:0:0` | 已准备好，用户未点赞 |
| `1:3:时间戳` | 已准备好，用户已点赞 |

状态 Hash 存在只说明加载过某个用户，不代表每个用户都已加载。

严格说，上述检查发现的是“数据缺失”，不能独立证明一定是首次使用。

### 6.4 每个用户都需要先手动 init 吗

正常首次使用时，直接调用当前点赞接口即可。Java 已在 `setLiked()` 中处理 `-2`，按需初始化后再执行点赞脚本。

保留 `BlogLikeCacheInitializer` 和初始化 Lua；不需要为了普通首次请求再专门编写一个手动预热接口。

每个用户对每篇笔记分别维护个人状态；同一篇笔记共享计数。

```text
A首次加载：计数装入20，补A的状态
A点赞：计数21
B首次加载：保留21，只补B的状态
B点赞：计数22
```

提前预热只是将正常首次加载提前执行，减少首个业务请求等待数据库的时间。它不能代替故障恢复。

### 6.5 初始化期间，别人点赞会不会被覆盖

假设A、B是两个不同用户：

```text
A查询MySQL，读到总数20，尚未执行初始化Lua
B先初始化，并点赞，Redis总数变成21
A执行初始化Lua，重新检查Redis，发现计数已存在，保留21
A只补自己的状态字段
A执行点赞Lua，读取当前21，再加一变成22
```

A传来的20只是备用初始值，不是每次必须写入的值。

如果A、B其实是同一个用户的两个点赞请求，先执行者修改状态后，后执行者会发现状态已经相同，直接返回，不会再加一。

### 6.6 Lua 原子性具体保护哪一段

保护的是每一次 Lua 内部的检查和写入，其他请求不能插到这段脚本中间。

Java 查询 MySQL 期间，其他用户可以继续操作；初始化 Lua 执行完到自己的点赞 Lua 开始之间，其他请求也可以执行。这两次 Lua 是分别执行的。

因此，“整段 initialize Java 方法都不能并发”不准确，“初始化Lua和之后的点赞Lua合起来是一个原子事务”也不准确。

## 7. 真正的点赞 Lua 做什么

`blog_like_set.lua` 的主要步骤：

1. 校验用户ID、目标状态和时间戳。
2. 检查 Key 类型与数据是否准备好。
3. 解析个人状态、版本和总数。
4. 目标状态与当前状态相同，返回0，保持原样。
5. 状态发生变化时，计算总数加一或减一，版本加一。
6. 写入个人状态、计数和最新 Outbox。
7. 返回当前状态、总数、版本。

为什么把这些操作放到 Lua 中：

```text
如果分开执行：
A判断用户未点赞
B也判断该用户未点赞
A增加一次计数
B也增加一次计数
```

Lua 将“判断 + 实际修改 + 记录待发送变化”放到同一次原子执行中，后一个请求会看到前一个执行后的状态。

把Outbox一起记录，还能消除应用进程在“状态已更新、计数已更新、尚未记录待发送变化”这几次调用之间退出的窗口。

不过，Lua原子执行指其他请求不能穿插；它不提供数据库式出错自动回滚。已有检查用于尽量在修改前排除参数、类型和数值范围错误。Redis自身的数据持久化与故障恢复仍需单独设计。

当前总数上限为 `2147483647`，与数据库实体及DTO的int对应；版本上限为 `9007199254740991`，控制在Lua可精确表达的整数范围内。拼接新版本时使用 `string.format('%.0f', newVersion)`。

## 8. 所有返回码

### 8.1 点赞脚本

成功返回四个值：

```text
{code, 当前点赞状态, 当前总数, 当前版本}
```

| code | 含义 | 当前Java处理 |
| --- | --- | --- |
| 1 | 状态发生变化，完成Redis写入 | 转换DTO，返回成功 |
| 0 | 已经是目标状态，保持原样 | 同样返回成功 |
| -1 | 请求参数不合法 | 参数异常 |
| -2 | Key或用户状态缺失，数据未就绪 | 调用初始化，再重试一次 |
| -3 | Key类型错误 | 停止并报错 |
| -4 | 状态格式异常，或个人状态与待发送状态不一致等 | 停止并报错 |
| -5 | 计数或版本超范围，包括本次减一会变负数 | 停止并报错 |

例如：

```text
点赞：     {1, 1, 21, 3}
重复点赞： {0, 1, 21, 3}
取消点赞： {1, 0, 20, 4}
```

错误只返回一个值，例如 `{-2}`。Java使用List接收，Lua返回的整数元素在当前接收方式下为Long，再转换成DTO。

### 8.2 初始化脚本

初始化脚本直接返回一个整数，不返回数组。

| code | 含义 |
| --- | --- |
| 1 | 本次完成初始化 |
| 0 | 当前用户数据已准备好，保留现有值 |
| -1 | 初始参数不合法 |
| -2 | 发现缓存部分缺失，或存在不适合直接初始化的残留数据 |
| -3 | Key类型错误 |

两个脚本的 `-2` 不完全相同：点赞脚本表示未就绪，Java会尝试初始化；初始化脚本返回 `-2` 时停止，不能继续当作普通首次加载。

Redis连接失败、网络超时等情况会抛异常，不会自动变成这些业务code。

## 9. 版本号解决什么问题

### 9.1 版本范围

每一对“用户ID + 笔记ID”独立递增：

| 用户 | 笔记 | 版本示例 |
| --- | --- | --- |
| 100 | 10 | 3 |
| 100 | 20 | 0 |
| 200 | 10 | 1 |

无关系记录时以0为基准；数据库已有版本5时，初始化沿用5。重复提交相同状态不递增，只有实际状态变化才加一。

### 9.2 拒绝迟到的旧消息

```text
用户先点赞：已点赞，版本1
用户再取消：未点赞，版本2
```

如果先处理版本2、后收到版本1，消费者应忽略版本1，避免旧点赞覆盖最新取消。

后续消费者规则：

```text
消息版本 > 数据库中同一关系的版本：接受
消息版本 <= 数据库版本：忽略
```

比较和更新需要数据库层的并发控制，不能只在Java先查询、判断后无条件更新。

### 9.3 版本决定接受，状态决定计数

| 数据库旧状态 | 接受的新状态 | 计数变化 |
| --- | --- | --- |
| 未点赞 | 已点赞 | +1 |
| 已点赞 | 未点赞 | -1 |
| 已点赞 | 已点赞 | 不变 |
| 未点赞 | 未点赞 | 不变 |
| 旧版本或重复版本消息 | 忽略 | 不变 |

例如数据库是“已点赞、版本3”，收到“已点赞、版本5”，需要推进版本，但不能再次加一。

版本号不是MQ消息ID。以后消息ID可以由 `blogId:userId:version` 组合得到，重发保持相同；这是后续约定，当前消息record尚未实现发布属性设置。

## 10. 查询为什么最后不用 Lua

今天最终决定：普通展示查询允许短暂不一致，使用两次普通Redis读取。

```java
String state = stringRedisTemplate
        .<String, String>opsForHash()
        .get(BlogLikeRedisKeys.state(blogId), userId.toString());

String countText = stringRedisTemplate.opsForValue()
        .get(BlogLikeRedisKeys.count(blogId));
```

两次读取之间可能发生点赞，所以结果可能来自略有差别的时点。当前接受这种展示差异。

查询Lua原本是为了同时读取状态与总数；今天没有继续采用，也没有在当前资源目录创建 `blog_like_get.lua`。

当前 `getLikeState()` 缺数据时，调用现有初始化类，再读一次。已有但格式错误的数据会报错，不会当成未点赞。

接受查询展示的短暂差异，不代表可以接受版本回退、重复计数或待发送变化丢失。

## 11. 初始化方法的事务注解

当前配置：

```java
@Transactional(
        readOnly = true,
        isolation = Isolation.REPEATABLE_READ,
        propagation = Propagation.REQUIRES_NEW
)
```

| 配置 | 在这里的作用 |
| --- | --- |
| readOnly=true | 声明数据库只读事务，允许相应优化；并非所有环境都会强制禁止UPDATE |
| REPEATABLE_READ | 在MySQL InnoDB中，两次普通查询使用同一事务中首次一致性读建立的快照 |
| REQUIRES_NEW | 使用独立事务；外层有事务时挂起外层，完成后恢复；仍在原线程执行 |

### 是否锁住两张表

这里使用普通SELECT，通过MVCC读取快照，不是把两张表锁住禁止别人修改。其他事务可以继续写入、提交。

例如：

```text
第一次查到总数20，建立快照
另一个事务将用户变成已点赞、总数改为21，并提交
第二次查询沿用旧快照，看到该用户仍未点赞
```

这样读到“20 + 未点赞”这个同一时间点的组合，避免混用修改前后的数据。

### 快照是否自动保证两张表业务正确

快照保证读取时点一致。写入方仍需在同一事务中维护关系和总数，才能提供正确的数据库基准。

如果数据库中原本就只修改关系、没更新总数，快照也会读取到原本不一致的数据。

### 为什么显式 REQUIRES_NEW

让初始化使用自己的隔离级别和新事务快照，避免继承外层事务已建立的旧快照。没有外层事务时，默认REQUIRED也会创建新事务，所以REQUIRES_NEW不是所有方法的必填设置。

该注解管理数据库事务，不会自动把Redis写入和MySQL绑成一个共同回滚的事务。后续通过注入的初始化Bean调用公共方法，让Spring事务代理生效。

## 12. 数据库和Redis为什么会短暂不同

正常首次使用的流程：

| 阶段 | MySQL | Redis |
| --- | --- | --- |
| 初始 | 未点赞、版本0、总数20 | 无数据 |
| 初始化后 | 未点赞、版本0、总数20 | 未点赞、版本0、总数20 |
| 点赞Lua处理后 | 未点赞、版本0、总数20 | 已点赞、版本1、总数21 |
| 未来MQ消费完成后 | 已点赞、版本1、总数21 | 已点赞、版本1、总数21 |

点赞处理后、落库前的差异来自异步方案本身。提前预热也不会消除这个阶段。

当前点赞MQ投递和消费者尚未实现，因此当前Redis发生的变化不会仅凭已定义的消息record就自动落库。

### 首次加载与故障恢复要区分

当前代码的缺失检查不足以区分所有情况：

```text
Redis已点赞，版本1，消息已进入MQ但数据库仍是版本0
Redis状态与计数随后丢失
查询把这当首次加载，从旧数据库恢复版本0
MQ稍后把数据库推进到版本1
Redis却仍停留在旧状态
```

这可能形成持续不一致。

初始化脚本已有部分完整性检查，但三个Key全都不存在时，无法仅靠这些Key证明是首次使用。检查也主要在Key层面，不能把它当作完整的异常恢复状态机。

`HSETNX`保护的是已有字段；字段真的丢失后，它不会自动知道丢失前的新版本。

后续需要明确首次加载和恢复入口。异常恢复时应协调未落库事件、重建基准与重新开放写入。查询可以降级读数据库展示，但不应在未知恢复状态下盲目重建写入基准。

Outbox为空也不一定证明数据库最新：消息可能已获发布确认、Outbox已清理，但消费者尚未落库。

Redis持久化、复制与消息恢复需要单独设计。若未落库状态及其可靠事件都已丢失，版本号和初始化无法凭空恢复它们。当前没有“零丢失”结论。

## 13. 接口、前端和验证

### 13.1 点赞与取消

```http
PUT http://localhost:8080/blog/10/like
Authorization: Bearer <当前登录token>
Content-Type: application/json

{"liked": true}
```

取消传 `false`。请求使用Boolean，缺少liked时可以识别为null并返回400，避免默认为false误取消。

用户ID从登录拦截器设置的UserContext获取，请求体不接收用户ID。已有内容服务鉴权范围覆盖 `/blog/**`。

返回示例：

```json
{
  "success": true,
  "errorMsg": null,
  "data": {
    "likedByMe": true,
    "liked": 21
  },
  "total": null
}
```

重复提交相同状态也会成功，不能把点赞Lua返回0理解为业务失败。

### 13.2 查询状态

约定地址：

```http
GET http://localhost:8080/blog/10/like
Authorization: Bearer <当前登录token>
```

无请求体，返回相同的BlogLikeDTO。

**已在 BlogController 中补上 GET 映射，调用现有 getLikeState Service。** Controller 方法如下：

```java
@GetMapping("/{id}/like")
public ResponseEntity<Result<BlogLikeDTO>> getLikeState(
        @PathVariable("id") Long id
) {
    try {
        BlogLikeDTO result = blogLikeService.getLikeState(id);
        return ResponseEntity.ok(Result.ok(result));
    } catch (IllegalArgumentException ex) {
        return ResponseEntity.badRequest()
                .body(Result.fail(ex.getMessage()));
    } catch (IllegalStateException
             | DataAccessException
             | TransactionException ex) {
        log.error("查询点赞状态失败，blogId={}", id, ex);
        return ResponseEntity
                .status(HttpStatus.SERVICE_UNAVAILABLE)
                .body(Result.fail("点赞状态暂不可用，请稍后重试"));
    }
}
```

重启内容服务加载新增映射后，前端就可以通过该接口恢复点赞状态。网关、用户服务及相关存储也需要运行。

### 13.3 前端做了什么

入口：我的 → 我的笔记 → 真实笔记详情。

- 尝试GET当前点赞状态。
- GET不可用时显示状态待确认，允许明确选择点赞或取消，不把读取失败当成未点赞。
- PUT携带登录Token及明确的liked值。
- 提交中禁用按钮，使用请求引用防止重复提交。
- 成功后使用服务端返回的状态和总数更新爱心。
- 网络、5xx或无效响应导致结果不确定时，显示待确认，不伪造成功或失败结果。
- 允许查询状态或手动重试相同目标，不自动重放写请求。
- 刷新查询失败时保留本页面上次确认的结果，并提示未刷新。
- 账号或笔记切换时，通过请求取消和身份检查避免旧响应污染新状态。

首页示例卡片的爱心仍是明确标注的内容预览；今天接入的是已发布真实笔记的详情。列表中的数据库计数和详情中的Redis计数在异步同步完成前也可能不同。

### 13.4 今日验证结果

前端构建通过；移动运行时28个受保护文件的完整性检查通过。

在独立无头浏览器中，用全部拦截的模拟业务接口验证了7个场景：

1. GET缺失时显示未知状态，不自动发送PUT。

6. 手动重试维持同一个目标状态。
7. GET可用后恢复返回的状态和总数。

这些是隔离模拟验证，没有调用真实后端，没有自动提交真实点赞。不能据此声称真实端到端联调、MQ一致性或点赞吞吐量已验证。今天没有新增点赞压测数据。

## 14. 后续MQ如何接：设计约定，尚未实现

消息结构已存在：

```java
public record BlogLikeChangedMessage(
        Long blogId,
        Long userId,
        Boolean liked,
        Long version,
        Long occurredAt
) {}
```

后续投递约定：

1. 扫描Outbox，读取某用户最新状态及版本。
2. 组装消息，发送RabbitMQ，检查发布确认与无法路由返回。
3. 发送失败保留记录重试。
4. 发布确认后，以Lua比较版本或完整快照再删除对应记录。
5. 若发送期间产生新版本，保留新记录，不能被旧回调删除。

发布确认表示RabbitMQ侧接受情况，不代表数据库已完成落库。

后续消费约定：

1. 验证消息字段。
2. 对相同用户和笔记比较数据库版本，处理重复、迟到消息。
3. 根据数据库旧状态与接受的新状态计算计数差额。
4. 在同一数据库事务中保存关系、版本与计数；批处理时需要并发控制和幂等设计。
5. 提交成功后才完成消费确认，失败按重试和死信策略处理。

消息重试、重复消费、按版本接受更新和Outbox条件清理是不同环节，不能用其中某一项代替整条链路的可靠性。

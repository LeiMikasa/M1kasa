# 巷里（M1kasa）项目需求文档

版本：0.1（前端原型完成后的产品与服务端需求基线）  
端形态：手机网页 / H5  
项目位置：`D:\M1kasa`

## 1. 项目定位

“巷里”是面向消费者的本地探店与优惠券平台。用户通过探店故事发现附近店铺，查看详情和限时优惠，完成抢购，并在个人页查看自己的故事、收藏与优惠。

本轮先交付了可运行的 H5 前端原型。页面使用真实视觉资源和演示数据，主要交互已经可操作；原有 Java 后端尚未接入。下一阶段在 `D:\M1kasa` 建立服务端模块，并按已选定的 **RabbitMQ** 方案改造异步下单。

## 2. 用户与核心路径

| 用户 | 目标 | 核心路径 |
| --- | --- | --- |
  | 游客 | 找到值得去的小店 | 推荐/附近 → 探店故事 → 店铺详情 |
  | 登录用户 | 购买限时优惠 | 店铺详情 → 优惠券 → 确认订单 → 订单状态 → 我的优惠 |
  | 内容创作者 | 分享探店体验 | 发布故事 → 上传图片 → 填写标题与正文 → 关联店铺 → 发布 |
  | 登录用户 | 管理个人内容 | 点赞/收藏/关注 → 我的故事/收藏/优惠 |

> 运营人员发布店铺和优惠券属于后续管理端范围，本轮消费者 H5 不提供运营后台。

## 3. 页面需求

### 3.1 首页与发现

- 顶部展示“巷里”品牌、搜索入口及“推荐 / 附近 / 关注”内容分类。
- 内容卡包含图片、作者、时间和位置、标题、摘要、点赞/评论/收藏、关联店铺与“看看这家店”按钮。
- “附近”按用户所在城市与距离展示；未授予定位时允许手动选城市。“关注”在无关注对象时显示引导空态。
- 点击故事进入详情，点击店铺卡或主按钮进入店铺详情。
- 需要加载、空结果和请求失败状态；图片加载失败时显示统一兜底资源。

### 3.2 搜索与附近

- 搜索支持店铺名称、故事标题与地区关键词。
- 搜索结果分店铺和故事，展示关键词、距离、评分或摘要。
- 附近页支持“全部 / 餐厅 / 咖啡馆”等分类和距离排序；真实定位须经用户授权。

### 3.3 故事详情与互动

- 展示图文、作者、关联店铺、评论列表。
- 登录后可点赞、取消点赞、收藏、取消收藏、关注作者和发布评论。
- 未登录操作引导至登录页，返回后继续原操作。
- 互动状态以服务端返回值为准，重复点击不得导致计数重复增加。

### 3.4 店铺与优惠券

- 店铺详情展示封面、名称、评分、人均消费、地址、营业时间、关联故事和优惠券列表。
- 优惠券展示名称、套餐内容、原价/优惠价、有效期、可购时间、库存/售罄状态和购买限制。
- 点击“抢购”进入确认订单页；售罄、未开始、已结束、已购买分别显示明确状态。
- 店铺资料与优惠券数据来自服务端；不得用前端展示库存作为抢购资格依据。

### 3.5 下单与订单状态

- 确认页展示店铺、优惠券、价格明细和使用规则。点击确认后禁用重复提交。
- 接口返回订单受理编号后进入“正在创建订单”状态；前端查询订单最终状态。
- 结果分为“成功 / 库存不足 / 重复购买 / 处理失败 / 暂时处理中”，可从个人页再次查看。
- 抢购资格和一人一单由服务端保证。前端不得在仅拿到受理编号时直接认定订单成功。
- 本轮原型以约 1 秒本地状态模拟排队与成功，**不产生真实订单或支付**。

### 3.6 发布与个人页

- 发布故事支持本地选图预览、标题和正文校验、关联店铺和提交状态。
- 个人页展示我的故事、收藏、优惠券及订单入口。
- 本轮原型的发布内容仅保留在当前页面会话中，刷新后会消失；正式版需服务端持久化。
- 消息页展示点赞、评论、关注及订单通知；未读数由服务端维护。

## 5. 原项目接口映射

当前 `hm-dianping` 代码库已存在店铺、探店、用户、关注、优惠券和秒杀订单等接口。下列路径按现有 Controller 整理，是迁移时的参考，不能直接视为新微服务接口契约。

| 前端需求 | 原项目参考接口 | 新项目需补充或调整 |
| --- | --- | --- |
| 店铺详情、分类和搜索 | `GET /shop/{id}`、`GET /shop/of/type`、`GET /shop/of/name`、`GET /shop-type/list` | 增加分页、城市/距离、统一错误码 |
| 故事列表与详情 | `GET /blog/hot`、`GET /blog/{id}`、`GET /blog/of/follow` | 明确推荐与附近排序策略 |
| 发布、点赞、关注 | `POST /blog`、`PUT /blog/like/{id}`、`PUT /follow/{id}/{isFollow}` | 增加评论完整接口、状态查询、幂等要求 |
| 图片上传 | `POST /upload/blog` | 接入统一存储与文件校验 |
| 登录与用户信息 | `POST /user/code`、`POST /user/login`、`GET /user/me` | 网关鉴权、登录状态和 Token 续期策略 |
| 店铺优惠 | `GET /voucher/list/{shopId}` | 返回活动时间、库存状态、限购规则 |
| 秒杀受理 | `POST /voucher-order/seckill/{id}` | 返回受理 ID/订单 ID 与状态语义；新增 `GET /orders/{id}/status` |

## 6. 服务端拆分建议

先围绕稳定业务边界拆分，避免为了拆分而拆分：

1. **gateway**：统一入口、路由、鉴权、限流和请求追踪。
2. **user-service**：登录、用户资料、关注关系。
3. **shop-service**：店铺、分类、搜索及缓存。
4. **content-service**：探店故事、评论、点赞、图片元数据。
5. **voucher-service**：优惠券与秒杀活动规则、库存资格。
6. **order-service**：订单创建、状态、查询及幂等消费。
7. **common**：只放稳定的协议、错误码、通用工具；不要共享数据库实体或跨服务业务实现。

消息中间件采用 RabbitMQ。原项目当前使用 Redis Lua 与 Redis Stream，并在消费侧使用 Redisson；**RabbitMQ 尚未进入当前代码**。迁移时需要先明确可靠投递与状态查询契约，再替换链路。

## 7. 秒杀与 RabbitMQ 目标链路

```text
H5 发起抢购
  → 网关鉴权与限流
  → voucher-service 用 Redis Lua 原子判断活动/库存/一人一单
  → 可靠记录下单意图
  → RabbitMQ 投递订单消息
  → order-service 幂等消费并在数据库事务中创建订单
  → 订单状态可查询
  → H5 展示最终结果
```

可靠性要求：

- Lua 成功与消息发布之间必须有恢复机制；不能只在内存中“先扣 Redis 库存、再直接发 MQ”。可将下单意图在同一个 Lua 脚本中写入 Redis Stream 作为可靠暂存，再由转发器投递 RabbitMQ；发布确认后才确认暂存记录。此处 Redis Stream 是投递暂存，不作为最终业务消费队列。
- RabbitMQ 开启持久化队列/消息、生产者确认、消费端手动确认、重试与死信处理。失败消息必须可追踪、可人工补偿。
- 消费端按业务键做幂等，数据库增加 `(user_id, voucher_id)` 唯一约束；重复消息不得生成第二笔订单。
- 数据库订单与库存变更在同一事务里处理；Redis 预扣与数据库结果出现差异时有对账及补偿流程。
- 前端展示的“处理中”是明确状态，必须提供超时后的查询与失败提示，不把 MQ 已接收当成订单成功。

## 8. 验收标准

1. 390 px 左右手机屏幕无横向溢出；底部导航、主按钮、系统安全区域不互相遮挡。
2. 用户可从首页进入故事、店铺、优惠券、确认订单和结果页，返回后信息保持一致。
3. 搜索可按关键词过滤并展示空结果；附近与关注空态可操作。
4. 表单要求标题与正文非空，照片可预览；发布成功后个人页能看到内容。
5. 接入服务端后，同一用户并发请求同一秒杀券只产生一笔订单；无库存不创建订单。
6. 重复 MQ 投递、消费者重启与短时故障后，订单结果最终可查询，失败消息可追踪。
7. 前端清楚区分“受理中”与“成功”；接口失败时可以重试或查询，不显示虚假的成功。

## 9. 交付顺序

1. 前端视觉和主要交互原型（本轮已完成）。
2. 确认接口契约、数据模型和错误码。
3. 在 `D:\M1kasa` 建立微服务骨架及基础设施。
4. 迁移店铺/内容/用户服务，联调 H5。
5. 接入 RabbitMQ 抢购订单链路，完成幂等、补偿和状态查询。
6. 联合验收、部署与性能测试。
